OAuth 2.1 + PKCE for the MCP server
====================================

Context
-------
The MCP server (ca-track-telemetry-mcp, Streamable HTTP, deployed on
Azure Container Apps) is currently the last unauthenticated endpoint in
the platform - anyone with the URL can call list_sessions,
get_session_detail, get_corner_metrics, compare_laps and read all
personal telemetry. This is a tracked v1.0 backlog item, unblocked now
that the information-security-due-diligence item closed. The fix: make
the MCP server an OAuth 2.1 Resource Server that validates bearer
tokens issued by the existing Entra External ID (CIAM) tenant
(tracktelemetry.ciamlogin.com, tenant id cc8e128a-ad5b-49af-a3ce-35e7c3c3e30c)
- the same tenant/pattern already used for the dashboard's MSAL sign-in
(ingest/api_auth.py).

Researched and confirmed before writing this plan:
- Entra ID/CIAM does NOT support OAuth Dynamic Client Registration
  (no /register endpoint, not on Microsoft's roadmap).
- Claude.ai's custom connector UI has an "Advanced settings" section
  that accepts a manually-configured OAuth Client ID + Client Secret
  for exactly this case (servers whose AS doesn't support DCR) - so no
  DCR proxy is needed.
- Claude's fixed OAuth redirect URI is https://claude.ai/api/mcp/auth_callback
- The pinned MCP Python SDK (mcp<2.0.0, resolves to 1.29.0) has
  first-class Resource-Server support: FastMCP(..., token_verifier=,
  auth=AuthSettings(issuer_url=, resource_server_url=,
  required_scopes=)). Confirmed by reading
  FastMCP.streamable_http_app() source in a throwaway venv: when
  token_verifier + auth.resource_server_url are set, it automatically
  wraps /mcp in RequireAuthMiddleware and publishes
  /.well-known/oauth-protected-resource (RFC 9728) advertising
  authorization_servers=[issuer_url] - exactly what an MCP client
  needs to discover where to authenticate. No hand-rolled routes
  needed.
- Container App FQDN: ca-track-telemetry-mcp.ambitiousgrass-8ff8b80e.eastus.azurecontainerapps.io

Approach
--------

1. New Entra CIAM app registration (resource server)

A SEPARATE app registration from the dashboard's - this is a distinct
resource (confidential client with a secret, not a SPA), and keeping
resource servers separate per-audience is the correct pattern, not a
shortcut worth avoiding.

Provision via Microsoft Graph REST calls (same DevTools-bearer-token +
curl pattern used earlier this session for the CIAM sign-up-flow
PATCH, since `az ad app create` against this tenant hits the same
Security-Defaults CLI block documented in the backlog):
  1. POST /v1.0/applications - display name track-telemetry-mcp,
     signInAudience matched to whatever the existing dashboard app
     (99a220cf-5739-4be8-8d68-55ebaa905ad3) uses (read via GET first).
  2. PATCH the new app: identifierUris: ["api://<new-app-id>"],
     api.oauth2PermissionScopes with one scope mcp.access (type User,
     admin+user consent display strings).
  3. PATCH web.redirectUris to add https://claude.ai/api/mcp/auth_callback
  4. POST /applications/{id}/addPassword - generate a client secret
     (Claude's Advanced Settings needs both client ID and secret).
  5. POST /v1.0/servicePrincipals with the new appId, mirroring
     whatever exists for the dashboard app.
Each step gets verified against Graph's actual response before moving
to the next, same as the sign-up-flow fix.

2. Server-side token verification

New file mcp_server/auth.py - an async TokenVerifier
(mcp.server.auth.provider.TokenVerifier) that validates bearer tokens
using PyJWT + PyJWKClient against the CIAM tenant, closely mirroring
the validation logic already proven in
ingest/api_auth.py::validate_bearer_token (JWKS-based signature check,
audience/issuer check, required-scope check on scp) but adapted to the
SDK's async verify_token(token) -> AccessToken | None contract instead
of Azure Functions' request/response shape. Reads MCP_TENANT_ID /
MCP_CLIENT_ID from env (new, separate from the dashboard's
MSAL_TENANT_ID/MSAL_CLIENT_ID even though the tenant value is the
same, since the client id differs and mixing the two would be
confusing). Required scope: mcp.access.

mcp_server/server.py changes:
  - from mcp_server.auth import EntraTokenVerifier (absolute import,
    matching the existing "from ingest import queries" convention
    that already works in this deployment).
  - from mcp.server.auth.settings import AuthSettings
  - FastMCP("track-telemetry", host="0.0.0.0",
    token_verifier=EntraTokenVerifier(),
    auth=AuthSettings(issuer_url=..., resource_server_url=os.environ["MCP_RESOURCE_URL"],
    required_scopes=["mcp.access"]))

mcp_server/requirements.txt: add PyJWT[crypto] (same dependency
ingest/api_auth.py already relies on for the dashboard).

3. Redeploy + new Container App env vars

az containerapp update adds MCP_TENANT_ID, MCP_CLIENT_ID,
MCP_RESOURCE_URL=https://ca-track-telemetry-mcp.ambitiousgrass-8ff8b80e.eastus.azurecontainerapps.io
alongside the existing SQL_SERVER/SQL_DATABASE, then redeploy via the
same `az containerapp up --source .` path documented in
docs/mcp_server.md.

4. Docs

Update docs/mcp_server.md: replace the "No auth for now" line with
the OAuth setup (env vars, the Entra app registration, and the
Claude.ai Advanced Settings client ID/secret step), and add the new
env vars to the deployment command block.
